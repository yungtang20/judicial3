## 一、架構原則與版本追溯鏈

依據規格書第 9.1 條，系統產出之任何正式公文與報告，均必須具備**端到端之不可變單一版本追溯鏈**：

```
[文件版本 (document_outputs)]
    ↓ (引用 template_version)
[模板版本 (statement_template_v1)]
    ↓ (關聯 analysis_run_id)
[分析執行 (analysis_runs)]
    ↓ (關聯 legal_candidate_id)
[候選法律方向 (legal_candidates)]
    ↓ (分解 legal_elements)
[法律構成要件 (legal_elements)]
    ↓ (對應 fact_id)
[結構化事實版本 (facts)]
    ↓ (對應 revision_id)
[原始案情版本 (case_revisions)]
```

若中間任何必要關聯缺失，系統立即阻止該文件通過正式核准。

## 二、P0-1 流程狀態機 (State Machine)

### 2.1 狀態定義
* `DRAFT`：草稿建立，可自由編修。
* `IN_REVIEW`：提交人工審核，等待公務員核准或退回。
* `APPROVED`：版本經人工確認核准（強制綁定 `target_revision_id`）。
* `CHANGES_REQUESTED`：審核不通過，退回修改（必須提供具體退回原因與修正要求）。
* `PROCESSING`：非同步或背景分析引擎執行中。
* `FAILED`：分析執行失敗（完整保存錯誤碼與重試上下文）。
* `STALE`：上游事實或法條依賴異動，舊有核准自動失效。
* `CANCELLED`：操作已撤銷。
* `ARCHIVED`：案件封存（軟封存，保留唯讀稽核權限）。

### 2.2 狀態轉移限制與檢查
1. **人工核准原子性**：僅限登入之案件擁有者手動執行，LLM 嚴禁自行觸發核准。
2. **依賴關係級聯失效（Cascading STALE Invalidation）**：
   - 當 Gate 1 事實遭修改或增刪，Gate 2～5 下游審核記錄自動切換為 `STALE`。
   - 舊版本完整保留於資料庫，絕不破壞歷史足跡。

## 三、Gate 0 至 Gate 5 循序作業規範

```
G0: 建立案件 (原始案情 SHA-256 數位指紋防竄改)
 ↓
G1: 事實整理 (ASSERTED / ADMITTED / DENIED / INFERRED / UNKNOWN 語意分離)
 ↓
G2: 法律分析 (PRIMARY 主位 / ALTERNATIVE 備位 / REJECTED 排除罪名及理由)
 ↓
G3: 問句規劃 (9 大類偵訊問句，對應待證要件與爭點)
 ↓
G4: 回答與重新分析 (受詢問人回答記錄，版本比對 Diff，版號累加)
 ↓
G5: 文件產生 (標準民國紀年條陳公文，字數與格式程式檢驗，Word / 文字匯出)
```

## 四、LLM 與程式邏輯的責任分離架構 (第 9.2 條)

| 模組工作 | 負責角色 | 控制機制 |
| :--- | :--- | :--- |
| 案情語意拆解、問句擬定建議、草稿條陳編撰 | LLM (語意生成層) | 提示詞版本管控，輸出視為不可信輸入 |
| 身分認證、權限檢查、狀態機移轉、版本綁定 | 後端程式 (業務控制層) | 伺服器端驗證、嚴格 Session 與 RLS |
| 法律法規檢索與條文版本核實 | 官方法規檢索模組 | 僅合規來源標記 VERIFIED，嚴禁捏造判決 |
| 候選罪名取捨、排除理由確認、調查方向裁定 | 司法警察 / 檢察官 (人工審核) | 強制人工確認核准方可進入次階段 |
| 條陳公文字數、段落順序、民國年號驗證 | 格式驗證器 (程式層) | 嚴格規則比對，輸出 PASS / FAIL 報告 |
| 雲端基礎架構變更、部署發布 | 專案維運工程師 | 嚴禁自動化部署，須經使用者明確授權 |
