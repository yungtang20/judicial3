## 一、專案基準與不可違反的原則

### 1.1 專案目標

建立獨立的繁體中文刑事偵查輔助網頁，協助使用者完成：

```
原始案情 → 結構化事實 → 證據整理 → 行為整理 → 法律規範查證 → 構成要件分析 → 候選法律方向 → 核心爭點 → 筆錄問句 → 回答與事實更新 → 重新分析 → 案情摘要 → 條陳與文件 → 人工確認。
```

本專案不以任何既有 GitHub 專案作為部署目標。`judicial2` 僅是可供參考的既有系統，不代表本專案可以直接沿用其程式碼、資料庫或雲端設定。

### 1.2 系統不可違反的原則

1. **不以案由定罪**：不得只依案由、罪章或關鍵字直接判定罪名。
2. **多重法律方向**：不得只產生一個候選方向而忽略合理替代方向。
3. **未知非否定**：不得把 `UNKNOWN` 當成 `FALSE`。
4. **否認非不存在**：不得把 `DENIED` 當成事實不存在。
5. **推論非證實**：不得把 `ASSERTED` 或 `INFERRED` 自動視為已證實。
6. **人工審核不可越權**：不得讓 LLM 自行決定是否跳過人工審核。
7. **歷史版本保護**：不得以新版本覆蓋或破壞歷史版本。
8. **真實查證標記**：不得引用未查證的法條或判決，卻標示為已驗證。
9. **審核狀態真實性**：不得將尚未審核的文件標示為正式完成。
10. **驗收非表面運作**：不得以網頁能開啟或部署成功代替完整驗收。
11. **未授權零變更**：不得在未經使用者明確授權時建立雲端服務、修改設定或執行部署。
12. **PASS 必有可重複檢驗證據**：所有 `PASS` 都必須有可重複檢查的證據。

### 1.3 狀態與術語

* **事實狀態**：描述陳述或認知狀態，不直接代表客觀真偽。
* **要件狀態**：描述法律構成要件目前的證據支持程度。
* **候選狀態**：描述候選法律方向在分析流程中的位置。
* **審核狀態**：描述人工是否確認特定版本。
* **流程狀態**：描述案件目前可以執行哪些操作。
* **版本**：不可混用的特定資料修訂或分析結果。
* **失效**：舊結果仍可追溯，但不再代表最新版本的有效審核結果。

這些狀態必須分開儲存，不得使用一個 `status` 欄位同時代表所有意義。

## 二、P0-1：流程與 Gate 狀態規格

### 2.1 修改理由
原始規格雖然定義 Gate 0～5，但未完整規定每個 Gate 的前置條件及必要輸出、人工核准的版本綁定、修改事實後的級聯失效、失敗恢復機制與退回作廢流程。

### 2.2 Gate 定義

| Gate | 階段 | 必要輸出 | 人工審核 |
| :--- | :--- | :--- | :--- |
| **G0** | 建立案件 | 原始案情及初始版本 | 確認案件資料完整 |
| **G1** | 事實整理 | 結構化事實、來源、未知及矛盾事項 | 必須 |
| **G2** | 法律分析 | 候選方向、法條、構成要件及核心爭點 | 必須 |
| **G3** | 問句規劃 | 各候選方向的核心、補強及區辨問句 | 必須 |
| **G4** | 回答與重新分析 | 回答、事實更新、候選變化及新爭點 | 必須 |
| **G5** | 文件產生 | 摘要、條陳及來源版本清單 | 最終確認必須 |

* G4 可因多輪問答重複執行。每輪問答均須建立新版本，不能直接修改已核准的舊版本。
* G5 的核准只代表特定文件版本經人工確認，不代表法院或其他機關已認定犯罪成立。

### 2.3 流程狀態機

案件流程狀態包含：
* `DRAFT`：草稿。
* `IN_REVIEW`：等待人工審核。
* `APPROVED`：目前版本已核准（必須綁定特定版本 ID）。
* `CHANGES_REQUESTED`：被退回修改。
* `PROCESSING`：分析正在執行。
* `FAILED`：操作失敗（保存錯誤紀錄與恢復資訊）。
* `STALE`：依據已變更，原結果過期。
* `CANCELLED`：操作已取消。
* `ARCHIVED`：案件已封存（非刪除，保留稽核權限）。

### 2.4 狀態轉移規則

| 目前狀態 | 事件 | 允許的下一狀態 | 條件 |
| :--- | :--- | :--- | :--- |
| DRAFT | 提交審核 | IN_REVIEW | 必要欄位通過驗證 |
| IN_REVIEW | 人工核准 | APPROVED | 核准者、版本及審核時間均已保存 |
| IN_REVIEW | 退回 | CHANGES_REQUESTED | 必須提供退回原因 |
| CHANGES_REQUESTED | 修改並重送 | IN_REVIEW | 建立新版本 |
| APPROVED | 上游資料變更 | STALE | 依賴版本已不一致 |
| STALE | 重新分析 | PROCESSING | 輸入版本已確定 |
| PROCESSING | 成功 | DRAFT 或 IN_REVIEW | 依任務類型決定 |
| PROCESSING | 失敗 | FAILED | 保存錯誤及執行紀錄 |
| FAILED | 重試 | PROCESSING | 原始輸入及重試條件仍有效 |
| 任意可封存狀態 | 封存 | ARCHIVED | 完成必要的資料一致性檢查 |

### 2.5 版本失效規則（依賴失效矩陣）

| 被修改的內容 | 必須標記失效的下游內容 |
| :--- | :--- |
| 原始案情 | 事實、行為、候選分析、問句、摘要、條陳 |
| 事實內容或狀態 | 相關行為、構成要件、候選排序、問句、摘要、條陳 |
| 證據內容或來源 | 依賴該證據的事實評估、候選分析、問句及文件 |
| 法條內容或適用版本 | 相關構成要件、候選分析、核心爭點及文件 |
| 候選法律方向 | 該候選的問句、候選摘要及相關文件 |
| 問句內容 | 該問句的審核及依賴它的回答關聯 |
| 回答內容 | 相關事實、候選分析、後續問句及文件 |
| 文件模板 | 依該模板產生的文件格式驗證及最終核准 |

## 三、P0-2：資料模型與 SQL Schema

### 3.1 核心資料表（20 張實體表）

1. `profiles`：使用者公務設定（auth_user_id 唯一）
2. `cases`：案件主檔（owner_id 外鍵）
3. `case_revisions`：原始案情不可變版本（(case_id, revision_number) 唯一）
4. `facts`：結構化事實（關聯案件與修訂版本，assertion_status CHECK 約束）
5. `evidence_items`：證據與來源物件
6. `fact_evidence_links`：事實與證據多對多關聯（複合主鍵）
7. `behaviors`：行為拆解（追溯來源事實）
8. `legal_sources`：法條、判決來源與查證狀態
9. `legal_candidates`：候選法律方向（PRIMARY/ALTERNATIVE/REJECTED 等）
10. `legal_elements`：構成要件分析（SUPPORTED/CONTRADICTED/UNRESOLVED 等）
11. `candidate_fact_links`：候選與事實多對多關聯（標記支持/相反/待查）
12. `core_issues`：爭點整理
13. `interview_questions`：9 大類警詢問句
14. `interview_answers`：受詢問人回答紀錄與修訂版本
15. `analysis_runs`：模型與規則引擎執行日誌
16. `review_records`：人工審核紀錄（綁定 target_revision_id，APPROVE/REQUEST_CHANGES/REJECT）
17. `document_outputs`：條陳與文件輸出版本
18. `audit_events`：安全稽核事件記錄
19. `prompt_versions`：提示詞版本管理（(task_type, version) 唯一）
20. `schema_migrations`：資料庫 DDL 遷移履歷

## 四、P0-3：法律推理與候選完整性

### 4.1 法律推理流程
解析案情 → 拆解事實 → 分離客觀/陳述/推論/未知 → 行為整理 → 檢索法律規範 → 驗證法條版本 → 拆解構成要件 → 建立要件事實對應 → 產製主位/備位/排除候選 → 生成爭點與 9 大類問句 → 人工審核。

### 4.2 候選狀態矩陣
* `PRIMARY`：目前最值得優先檢視之主位罪名。
* `ALTERNATIVE`：具合理法律解釋空間之備位或競合罪名。
* `LOW_CONFIDENCE`：關聯要件尚不清楚之方向。
* `UNRESOLVED`：資料不足待查方向。
* `REJECTED`：經具體法理審查排除之罪名（強制填寫排除理由）。

## 五、P0-4：條陳模板與程式驗證

### 5.1 模板與內容分離
* 內容生成層：依案件資料產製客觀事實與法律爭點。
* 格式組裝層：依標準模板（如 `statement_template_v1`）生成並執行驗證。
* 嚴格驗證器檢查：段落順序、必填欄位、民國年號、字數與未審核標記。

---

## 六、P0-5：安全與備份驗收

### 6.1 安全架構
* 單一公務員指定帳號身分驗證，防暴力破解鎖定。
* 案件行級安全控制（RLS）與伺服器端授權。
* 應用程式層信封加密（AES-256-GCM），金鑰與密文嚴格物理隔離。
* 外部 AI 集中式傳輸閘門：預設關閉（`ALLOW_EXTERNAL_AI=false`）。
* 備份與復原演練：定義 RPO / RTO 目標並於隔離環境驗證。

## 七、P1：測試規格與分階段開發

### 7.1 測試四態標準
* `PASS`：已實際執行，符合規格，且附有不可竄改之檢查證據。
* `FAIL`：已實際執行，結果不符合規格。
* `NOT_RUN`：尚未執行。
* `BLOCKED`：因前置條件缺失而受阻無法執行。

### 7.2 分階段開發路線圖（P0～P9）
* **P0**：規格確認
* **P1**：本機應用骨架
* **P2**：認證與資料層
* **P3**：案件與事實流程
* **P4**：法律分析與問句
* **P5**：文件與條陳
* **P6**：安全及復原
* **P7**：部署前稽核
* **P8**：雲端部署（需經使用者明確授權）
* **P9**：部署後驗收
